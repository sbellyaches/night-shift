      22:00 · Chapter 1

      The firewall is an agent

      Incident · 22:04 · a blocked address got in
      S
      Sam · team lead

      Something just got through the firewall. Look at this.

      ALERT · firewall
      22:04suspicious traffic from203.0.113.7 toweb server, port 443 resultALLOWED note203.0.113.7 is on the block list

      An address on the block list got through the firewall. Every minute that door stays open, the attacker can try more of our machines.

      Nobody broke into the firewall. It did exactly what its rules told it to do. To see why, we need the most basic idea in AI: the agent.

      22:00 · Chapter 1

      Sense, decide, act

      An agent is anything that perceives its environment through sensors and acts on it through actuators, like a guard at a door who looks, decides and acts, again and again. What the sensors report at one moment is called a percept.

      agent loop

      A firewall fits this exactly. Its percept is the header of one packet: where it comes from, where it's going and which port it wants. Its actions are allow, block and log. Then the next packet arrives, and the loop starts again.

      Engineers describe an agent's job with a PEAS card:

      PPerformance measurestop attacks and let real users through
      EEnvironmentthe network and everyone using it
      AActuatorsallow, block, log
      SSensorspacket headers

      22:00 · Chapter 1

      Rules, read from the top

      The simplest kind of agent is a simple reflex agent. It applies IF-THEN rules to the current percept and nothing else. A firewall reads its rules from the top and stops at the first one that matches.

      firewall.rules
      #matchaction
      1port 443, any sourceALLOW
      2source 203.0.113.7BLOCK
      3anything elseBLOCK

      Here comes the packet from the alert. Rule 1 matches first, so the packet is allowed. Rule 2, written for exactly this address, is never even read.

      Swap the first two rules and the same packet is blocked. The agent wasn't broken. Its rules were in the wrong order.

      Any chain of IF-THEN rules works like this. An office climate system with the rules "heat below 20 °C", "cool above 26 °C" and "fresh air above 1,000 ppm of CO₂" never turns on the fresh air on a cold, crowded morning, because the heating rule fires first.

      22:00 · Chapter 1

      From reflexes to memory

      Reflex agents are fast, but they forget everything after each percept. AI describes four kinds of agents, and each one can do more than the one before.

      1 · Simple reflex

      IF-THEN rules on the current percept. The packet filter we just looked at.

      2 · Model-based

      Keeps an internal state, so it remembers what it can't see right now. A stateful firewall keeps a table of open connections and lets a reply in only if someone inside asked for it.

      3 · Goal-based

      Imagines future states and searches for actions that reach a goal. That's the next hour.

      4 · Utility-based

      Scores outcomes with a number, so it can weigh goals against each other, like safety against speed. That's the last hour of the night.

      The firewall's world is a hard one. It is partially observable: it sees headers, not intentions. It is multi-agent, because attackers adapt. It is stochastic, because it can't predict what arrives next. And it is dynamic: traffic keeps flowing while it decides.

      A rational agent picks the action with the best expected performance, given what it has perceived so far. Rational doesn't mean all-knowing. A firewall that reads only headers can't know what a packet is for, and it can still be rational.

      22:00 · Our move

      Fix the rule order

      firewall · after the fix
      What we did

      We moved the block rule above the allow rule. Now the firewall checks the attacker's address before it looks at the port, and the attacker's packets bounce off.

      Why this idea fits

      Seeing the firewall as an agent (sense, decide, act) showed exactly which part failed. Its senses were fine: it read the attacker's address. Its decision was wrong, because the rules were checked in the wrong order. Once you know which part failed, the fix is small.

      Remember

      • An agent senses, decides and acts, over and over.
      • Reflex rules are read from the top. The first match wins, so the order of the rules matters.
      • Memory, goals and utilities make agents smarter, but none of them sees everything.

      Mapping the way in

      Incident · 23:10 · attacker on the web server
      S
      Sam · team lead

      They're on the web server. If I were them, I'd go for the payments database next. We need their route before they find it.

      attack-paths.txt
      web server  → mail server  effort 2
      web server  → VPN gateway  effort 8
      mail server → payments DB  effort 10
      VPN gateway → payments DB  effort 1

      Each line is a move the attacker could make, and the number is the effort it takes: hours of work, say. The lower the total, the more likely the attacker is to take that route.

      Finding the easiest way from the web server to the database is a search problem. It's the same problem as finding a route on a map, just with machines instead of cities.

      23:00 · Chapter 2

      Search and the frontier

      A search problem has a state space (here, the machines), actions with costs (the moves), a start and a goal test. A solution is a sequence of actions from the start to the goal.

      search.pseudo
      frontier ← [start]
      while frontier is not empty:
        route ← take one route out of frontier ← the choice
        if route ends at the goal: return route
        add each one-step-longer route to frontier

      The frontier is a to-do list: routes that have been found but not explored yet. Search strategies differ in only one thing, which route they take off the list next.

      strategies
      BFSoldest route first (a queue)
      → fewest steps
      DFSnewest route first (a stack)
      → little memory, any route
      UCScheapest route so far, g(n)
      → cheapest route
      A*lowest g(n) + h(n)
      → cheapest route, usually faster

      23:00 · Chapter 2

      Wide or deep?

      The two simplest strategies explore in opposite ways. Here both map the machines reachable from the web server, and the numbers show the order in which each one checks them.

      exploration order

      Breadth-first search (BFS) checks everything one step away, then everything two steps away, like ripples spreading on water. Its to-do list is a queue: first in, first out, like a line at a shop.

      Depth-first search (DFS) follows one path as far as it goes, then backs up and tries the next one, like walking a maze: down one corridor to the end, then back to the last turn. Its to-do list is a stack: last in, first out, like a pile of plates.

      DFS remembers little more than the path it's on, so it needs very little memory. But it returns the first route it finds, not the best one, and without a list of visited machines it can go round in circles forever. Iterative deepening fixes that: run DFS with a depth limit of 1, then 2, then 3. It keeps the small memory of DFS and finds the shallowest answer, like BFS.

      23:00 · Chapter 2

      Fewest steps or least effort?

      attack-path.search

      BFS spreads in layers. It reaches the database through the mail server: two moves, the fewest possible, but effort 2 + 10 = 12.

      Uniform-cost search (UCS) takes the cheapest route so far. The mail server (2) goes first and reaches the database at 12. But the VPN gateway, at 8, is still cheaper than 12, so it goes next and reaches the database at 9.

      Same network, two answers. BFS finds the cheapest route only when every move costs the same. UCS always finds it, as long as costs are positive. DFS would simply follow whichever branch it tried first down to the database, so here it could return either route, 12 or 9, by luck.

      23:00 · Chapter 2

      A* adds a good guess

      UCS only looks back, at the effort spent so far, g(n). A* also estimates the effort still needed, the heuristic h(n), like a driver who counts the distance already driven plus a rough guess of what's left. It takes the route with the lowest f(n) = g(n) + h(n).

      a-star.frontier
      route 1g 4 + h 8 = f 12
      route 2g 7 + h 2 = f 9

      Route 2 has cost more so far, but it's almost there, so A* explores it first. With h = 0, A* is exactly UCS.

      The guess must never be bigger than the real effort left: 0 ≤ h(n) ≤ h*(n). Such a heuristic is admissible, and with it A* always returns the cheapest route. On a grid, counting the steps left (the Manhattan distance) is a classic admissible guess. A heuristic that overestimates can return a worse route.

      Defenders map whole networks as graphs and search them for the cheapest attack paths to their most important systems. Internet routers solve the same kind of problem all the time: the OSPF routing protocol uses Dijkstra's algorithm, which is essentially UCS.

      23:00 · Our move

      Guard the cheapest path

      attack-path · predicted
      What we did

      UCS showed that the attacker's easiest way to the database runs through the VPN gateway, effort 8 + 1 = 9. So that's where we put our closest watch and a tripwire. If they come that way, we'll see them at once.

      Why this idea fits

      An attacker inside a network is like a burglar in a building, looking for the easiest way to the safe. Search goes through the possible routes in an orderly way, so we found that route before they did. We used UCS, not BFS, because the moves cost different amounts of effort, and the route with the fewest steps isn't the easiest one.

      Remember

      • The frontier is a to-do list. The strategy decides which route comes off it next.
      • BFS goes wide and DFS goes deep. UCS finds the lowest cost.
      • A* ranks routes by f = g + h. With an admissible h it still finds the cheapest route, usually faster.
      S
      Sam · team lead

      Eyes on the VPN gateway. If they go for the database, that's the way they'll come.

      00:00 · Chapter 3

      Good enough, fast

      Incident · 00:05 · a slow scan is slipping past the detector
      S
      Sam · team lead

      They've switched to a slow, quiet scan, and our intrusion detector isn't catching it. We need a better sensitivity setting. Each test replays a chunk of traffic and takes about ten minutes, so we can't try all seven.

      ids-tuning.log
      setting  0  1  2  3  4  5  6
      score    ?  ?  ?  ?  ?  ?  ?

      This time the answer is a setting, not a route. Each test gives a setting a score: how well it catches the scan in a replay of tonight's traffic without raising false alarms. Higher is better.

      For problems like this, local search is enough: keep one complete candidate, try small changes to it (its neighbours), and score each one with an objective function. It's like turning a radio dial until the signal is clearest, and it needs almost no memory.

      00:00 · Chapter 3

      Hill climbing

      The simplest local search is hill climbing: move to a better neighbour, and stop when no neighbour is better.

      hill-climb

      Start at setting 0, score 1. Its neighbour scores 3, so move. Then 5, then 8. Both neighbours of the 8 are lower, so hill climbing stops at setting 3.

      It only ever looks one step around itself. That makes it fast and almost memory-free, and also short-sighted.

      00:00 · Chapter 3

      When the hill is the wrong one

      That time the first peak was the highest one. Often it isn't.

      landscape

      A local maximum is better than all its neighbours but not the best overall. The climber stops there for good. Flat plateaus and narrow ridges, where you'd need several moves in a row to improve, stop it too.

      On the classic 8-queens puzzle, steepest hill climbing from a random start solves only about 14% of cases and gets stuck in the other 86%, although it's quick: about 4 moves when it succeeds.

      One way out is random restarts: climb again from new random starting points and keep the best result. With a 14% chance per climb, about 7 climbs are needed on average.

      00:00 · Chapter 3

      Simulated annealing

      Hill climbing never takes a step down, so the first small hill can trap it. Simulated annealing gets out by sometimes taking a worse step on purpose.

      annealing
      temperature
      hot: takes worse stepscold: only better ones

      At first the search is "hot": it often accepts a worse step. That lets it walk down off the small hill and find the higher one.

      Then it slowly "cools down" and accepts worse steps less and less, the big ones least of all. By the end it only takes better steps, like plain hill climbing, and settles on the top it has found.

      The name comes from metalwork. Annealing means heating metal or glass and cooling it slowly, so its atoms can settle into an orderly structure. Cool too fast, and the search, like the metal, freezes in a bad spot.

      Local search turns up all over computing. It cracks old substitution ciphers in capture-the-flag contests, shortens delivery routes by swapping stops, and, as gradient descent, trains most machine-learning models.

      00:00 · Our move

      Set the detector to 3

      ids · sensitivity
      What we did

      We tested one setting at a time, each one step up from the last. The score rose from 1 to 3 to 5 to 8. At setting 4 it fell to 6, so going further only made things worse. We stopped and set the detector to 3. Five tests, and at 00:56 it caught the slow scan.

      Why this idea fits

      Too low a setting misses a quiet scan. Too high a setting buries us in false alarms. The best setting is somewhere in between, and every test cost ten minutes the attacker could use. Hill climbing tunes it the way you tune a radio: keep turning while the sound gets clearer, and stop when it gets worse. It doesn't promise the best setting there is, but it finds a good one with few tests.

      Remember

      • Local search keeps one candidate and improves it with small changes.
      • Hill climbing is fast but stops at local maxima, plateaus and ridges.
      • Random restarts and simulated annealing help it escape.

      01:00 · Chapter 4

      Think like the attacker

      Incident · 01:00 · attacker probing the VPN gateway
      S
      Sam · team lead

      We can harden the gateway three ways, and whatever we pick, they'll answer. We need the option that holds up against their best reply.

      hardening.plan
      option Astaff only, with a second login step option Bkeep it open, watch it closely option Cmove it behind another firewall scorehow safe we end up, from our risk sheet: higher is better

      That's a game: two sides take turns, and one side's gain is the other's loss. In a zero-sum game, one number, the utility, scores every ending.

      We are MAX and want the highest score. The attacker is MIN and wants the lowest. We move first, and the attacker replies. It's like chess: before you move, you think about your opponent's best answer.

      01:00 · Chapter 4

      Minimax

      All moves and replies form a game tree, with the score of every ending at the bottom.

      game-tree

      For each of our options, assume the attacker picks the reply that's worst for us: min(3, 12, 8) = 3, min(2, 4, 6) = 2 and min(14, 5, 2) = 2.

      Then we pick the option whose worst case is best: max(3, 2, 2) = 3. That's the minimax value. Against an opponent who always plays their best, nothing guarantees more.

      The 14 looks tempting, but that branch belongs to the attacker, who would answer with the 2. Minimax plans for what we can be sure of.

      01:00 · Chapter 4

      Pruning and depth limits

      Minimax looks at about bm positions, where b is the number of moves per turn and m the number of turns. That grows very fast.

      alpha-beta

      Alpha-beta pruning skips branches that can't change the decision. Option A already guarantees 3. In option B the attacker's first reply gives 2, so B can never beat A, and its 4 and 6 are never looked at. Same answer, less work: with a perfect move order, about bm/2 positions.

      Real games are far too big to search to the end. So the search stops at a depth limit and scores the position with an evaluation function, usually a weighted sum of features: Eval(s) = w₁f₁(s) + … + wₙfₙ(s). Danger just past the limit stays invisible. That's the horizon effect.

      01:00 · Chapter 4

      When the other side is chance

      Minimax assumes an opponent who thinks. When the next event is random, like a disk failing, expectimax uses chance nodes that average the outcomes, weighted by their probabilities.

      expectimax
      ½ · 8 + ⅓ · 24 + ⅙ · (−12) = 4 + 8 − 2 = 10

      Plan for the worst reply against someone who plays against you, and for the average against luck.

      Game search made history. IBM's Deep Blue beat world chess champion Garry Kasparov in 1997, AlphaGo beat Lee Sedol at Go in 2016 by combining search with learned evaluations, and checkers was solved in 2007: with perfect play on both sides, it's a draw.

      Why this idea fits

      The attacker is a thinking opponent who reacts to every move we make. Minimax plans for their best reply, so there are no nasty surprises. If the other side were just bad luck, like a disk failing, we would plan for the average with expectimax instead.

      Remember

      • Minimax plans for the opponent's best reply.
      • Alpha-beta gets the same answer with less work.
      • Big games need depth limits and evaluation functions. Chance needs expectimax.

      02:00 · Chapter 5

      The bot that learns

      Incident · 02:07 · stolen login used on laptop-14
      S
      Sam · team lead

      A stolen login just showed up on laptop-14. No time to think it through by hand. Watch what the response bot does.

      response-bot.log
      02:07:12stolen login on laptop-14 optionswatch · reset password · isolate 02:07:13choosing

      A stolen login can spread to other machines fast, sometimes within minutes, faster than people can meet and decide. So the company lets a response bot make the first move, and people check it afterwards.

      Nobody wrote the bot a rule for this. It learned what to do from practice. To see how, we first need a way to describe a chain of decisions where nothing is certain: the Markov decision process, or MDP.

      02:00 · Chapter 5

      A chain of decisions

      Here is the bot's situation as an MDP. The box at the top is a state: a situation the bot can be in. From there it can take one of three actions.

      laptop-14 · options

      Results aren't certain. A password reset usually locks the attacker out, but if they have already moved on, it's too late. And the attacker gets a move too.

      Every step earns a reward, a score that can be negative. Each minute the attacker is inside costs a little, and containing them is worth a lot. A discount factor makes sooner rewards count a bit more than later ones.

      The answer to an MDP isn't one plan. It's a policy: what to do in every state. When something doesn't go to plan, the policy already says what to do next.

      How good is a state? Its value is all the reward you can expect from it if you act well. The Bellman equation says it in one line: value = reward now + the discounted value of where you end up. That's why a state can pay nothing by itself and still be worth a lot.

      02:00 · Chapter 5

      How the bot learned

      Nobody handed the bot the odds and rewards of every move. It learned them by reinforcement learning: practising on thousands of simulated incidents, the way a new colleague learns from experience.

      bot · learned scores
      watch
      reset password
      isolate

      Each round it tries an action, sees what happens, and nudges its score for that action up or down. Early on the scores are guesses: in one round, watching looked fine because the attacker was slow. After many rounds they settle, and isolating comes out on top.

      These scores are called Q-values: how good an action is in a state, counting everything that tends to follow. Updating them after every try is Q-learning, and the learning rate sets how big each nudge is.

      To find better moves, the bot sometimes tries a random action instead of its favourite. That's ε-greedy exploration: mostly do what works, and now and then try something new.

      In 2015, DeepMind's deep Q-network learned dozens of Atari games from the screen pixels alone. The field also has a warning: a bot chases the reward it's given, not the one you meant. Reward it only for a quiet alert screen, and it may learn to switch the alerts off.

      02:00 · Our move

      Isolate laptop-14

      network · 02:07

      The bot cut laptop-14 off from the network within seconds. We checked its choice, kept it, and reset the stolen password.

      Why this idea fits

      Nobody can write a rule for every kind of incident. The bot practised on many simulated incidents and learned which action pays off in the long run, not just right now. Isolating a laptop costs a little work today. A stolen login spreading through the network would cost far more.

      Remember

      • An MDP describes a chain of decisions with uncertain results. Its answer is a policy.
      • A state's value is the reward now plus the discounted value of what comes next.
      • Q-learning learns the value of each action by trying, and ε-greedy keeps it exploring.

      03:00 · Chapter 6

      A thousand alerts

      Incident · 03:00 · 1,085 alerts in the queue
      S
      Sam · team lead

      They're flooding us with noise to hide in it. Over a thousand alerts, and we can't read them all. Which ones are real?

      alert queue
      events10,000 tonight alerts1,085 real?

      An alert is a clue, not proof. Some alerts are attacks. Many are normal work that just looks odd. Probability is how we measure how much a clue should change our mind.

      The tool for that is Bayes' rule. As a formula it looks like maths, but the idea is simple, and the easiest way to see it is to count.

      03:00 · Chapter 6

      Count, don't calculate

      Our detector is good: it catches 95 of every 100 attacks. But it also flags about 1 in 10 normal events by mistake. And real attacks are rare: about 1 event in 100.

      10,000 events

      Picture 10,000 events. About 100 are attacks, and the detector flags 95 of them. The other 9,900 are normal, and 1 in 10 of those gets flagged too: 990 false alarms.

      So of 1,085 alerts, only 95 are real: fewer than 1 in 10. The detector isn't bad. Attacks are just rare, and the false alarms come from a much bigger pile.

      That is Bayes' rule at work. Start from how common something is: the prior. Weigh the clue: how much more often it shows up during an attack than during normal work, the likelihood. The result is your updated belief: the posterior.

      This base rate effect is one of the main reasons intrusion detection is hard. Doctors meet it too: a good test for a rare illness still gives many false alarms.

      03:00 · Chapter 6

      Explaining away

      A Bayesian network draws beliefs as a map. Arrows run from causes to effects, and each arrow carries a small table of how likely the effect is for each cause. That lets a computer combine many clues at once.

      one alert · two possible causes

      We see a big data transfer at 03:00. Both causes become more likely: maybe an attacker is copying data, maybe it's the backup.

      Then we check the schedule: the nightly backup was running. That already explains the transfer, so an attacker becomes unlikely again. This is explaining away.

      That's how hundreds of alerts sank down our list: each one already had an innocent cause. Spam filters use Bayes' rule in a similar way, weighing the words in an email.

      03:00 · Our move

      alert queue · ranked

      Instead of reading 1,085 alerts in order, we ranked them by how likely each one was to be real. Alerts explained by the nightly backup job sank to the bottom. At the top: traffic from db-02 to an unknown address.

      Why this idea fits

      An alert is a clue, not proof. Counting showed that most alerts are false alarms, simply because real attacks are rare. Explaining away pushed down every alert that already had an innocent cause, like the backup job. What stayed on top had no innocent explanation at all. That turned an impossible pile into a short list.

      Remember

      • Start from the base rate. Rare events stay rare, even after a good clue.
      • Bayes' rule: begin with how common something is, then update with the evidence.
      • In a Bayesian network, one confirmed cause can explain another away.

      04:00 · Chapter 7

      Is it infected?

      Incident · 04:00 · db-02 running hot
      S
      Sam · team lead

      db-02 has been running hot for an hour. Are they on it? If we log in to check, we tip them off. All we have are its CPU readings.

      db-02.cpu
      03:00HIGH 04:00HIGH state? hidden

      Why would the CPU tell us anything? An attacker's tools, copying data or cracking passwords, keep a server busy. But so do backups and night reports, so one busy hour proves nothing. It's like guessing whether someone is home from the lights in their window.

      The true state, clean or compromised, is hidden. All we get are noisy readings. That's a hidden Markov model, or HMM. It needs three things: the starting probabilities, the transition probabilities (how the hidden state changes from one reading to the next) and the emission probabilities (how likely each reading is in each state).

      04:00 · Chapter 7

      The model

      hmm

      The arrows are the transitions, from one hourly reading to the next. A clean server stays clean with 0.9 and gets broken into with 0.1. A compromised one is cleaned up by our tools with 0.2 and stays compromised with 0.8. The Markov assumption says the next state depends only on the current one.

      The lines at the bottom are the emissions. Night jobs make a clean server read HIGH in 2 hours out of 10. An attacker's tools make a compromised one read HIGH in 7 out of 10. Careful: that 0.7 is the chance of HIGH given compromised, not the chance of compromised given HIGH. To turn it around, we need Bayes again.

      04:00 · Chapter 7

      Filtering

      Filtering keeps a running guess about the hidden state. With every reading it does four things: predict (the state may have changed since the last hour), observe (read the CPU), correct (favour the state that explains the reading better) and normalize (rescale so the chances add up to 100%).

      db-02 · belief
      start
      high
      high
      no reading
      ■ clean■ compromised

      Start: 0.8 clean, 0.2 compromised. The first reading is HIGH, so multiply by how likely HIGH is in each state, 0.8 × 0.2 = 0.16 and 0.2 × 0.7 = 0.14, then normalize: [0.533, 0.467].

      Predict one step with the transitions, then correct with the second HIGH: [0.277, 0.723]. db-02 is now probably compromised.

      No new reading? Then we can only predict: one step later it's [0.394, 0.606]. Without evidence, the belief drifts back.

      That's what we did all night with db-02: every hour, a new reading and an updated guess. Navigation apps use the same idea to track a car from noisy GPS fixes.

      04:00 · Chapter 7

      Looking back

      Smoothing uses later readings to revise earlier states, the way a detective rereads early clues after learning more. After HIGH, HIGH, the chance that db-02 was already compromised at the first reading rises from about 47% to about 68%.

      viterbi · readings HIGH, HIGH
      clean → clean0.0288
      clean → compromised0.0112
      compromised → clean0.0056
      compromised → compromised0.0784

      The Viterbi algorithm finds the single most likely story: the sequence of hidden states that best explains all the readings. It works like filtering, but keeps only the best path into each state and then traces it back. Here the story is compromised, then compromised: the attacker was probably on db-02 before our first reading. That tells the investigators where to start looking.

      HMMs watch over machines, were the backbone of speech recognition for decades, and help robots work out where they are from noisy sensors.

      05:00 · Chapter 8

      Where the malware score comes from

      Machine learning learns rules from data. Supervised learning learns from labelled examples, unsupervised learning finds structure without labels, and reinforcement learning learns from rewards, like the response bot. Predicting a number is regression; predicting a class is classification.

      The scanner is a classifier built with logistic regression: it weighs the file's features, adds them up, z = wᵀx + b, and turns z into a probability with the sigmoid, σ(z) = 1 / (1 + e−z).

      sigmoid

      σ(−2) ≈ 0.119, σ(0) = 0.5 and σ(2) ≈ 0.881. The file on db-02 scored z = 2, so its malware score is 0.88.

      A decision threshold turns the probability into yes or no, and it's a policy, not a law of nature. When a missed threat is expensive, you might flag files from 0.2 upward.

      05:00 · Chapter 8

      Accuracy can lie

      Say 2 of every 100 files are malicious.

      100 files

      These two red squares are the real threats.

      A model that always says "clean" is right 98 times out of 100. Its accuracy is 98%, and it catches nothing.

      That's why we look beyond accuracy, (TP + TN) / N. Recall = TP / (TP + FN) says how many real threats were caught. Precision = TP / (TP + FP) says how many alarms were real. F1 balances the two.

      Other classic models: a decision tree asks if-then questions about the features (easy to read, but it can overfit, learning the noise in its data), a random forest lets many trees vote, and K-means groups data without labels. The usual traps are overfitting, leakage (the answer sneaking into the training data) and a world that changes after training.

      05:00 · Chapter 8

      Maximum expected utility

      A rational agent picks the action with the highest expected utility: EU(a) = Σ P(o | a) · U(o). That's the rule of maximum expected utility, the way you'd weigh odds and costs before deciding to take an umbrella.

      expected-utility
      Project A · 0.9·100 + 0.1·(−20)
      EU = 88
      Project B · 0.6·200 + 0.4·(−50)
      EU = 100 → choose B

      B fails more often and is still the better bet. A decision is judged by what you knew when you made it, not by how it turned out.

      The same idea gives a simple rule for acting on a risk: act when the probability of the bad outcome is higher than the cost of acting divided by the cost of the bad outcome. With $2,000 of downtime against a $10,000 breach, that's 2,000 / 10,000 = 20%. Or the other way round: at a 15% risk of a $20,000 breach, the expected loss is 0.15 × 20,000 = $3,000, more than $2,000, so you act.

      What we did

      We took db-02 offline. Keeping it running meant a 72% chance of a $10,000 breach, an expected loss of $7,200. Taking it offline cost $2,000 of downtime, so that was the cheaper choice. Put another way, 72% is far above the 20% threshold. And it cut the attacker off from the payments data.

      Why this idea fits

      A prediction alone doesn't tell you what to do. Expected utility weighs how likely each outcome is against what it would cost, so the decision depends on both the odds and the stakes. A small chance of a huge loss can be worth acting on. Here the chance wasn't even small.

      Remember

      • A classifier predicts. A decision weighs the prediction against costs.
      • Accuracy alone can hide a useless model. Check precision and recall.
      • Choose the action with the maximum expected utility.
